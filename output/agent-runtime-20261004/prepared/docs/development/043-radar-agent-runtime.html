RADAR Agent Runtime

Objetivo e problema

Permitir que o Plane inicie e acompanhe uma execução do agente com contexto autorizado. O adapter anterior atendia ao caminho inverso: o CoS usava os commands do RADAR. A execução do produto agora possui contrato próprio, sem depender da API de simulação.

Arquitetura

Sessão Plane → membership + vínculo + grant → snapshot limitado
                         ↓
                fachada agent-runtime
                         ↓ Bearer servidor a servidor
COS_AGENT_V2 → RadarAgentRuntime → DeepAgentsAdapter → motor existente
                         ↓
                 ledger de runs + eventos

O Plane controla autoridade e dados; o CoS controla execução. As estruturas públicas são JSON com tipos de produto. BaseMessage e estados LangGraph ficam no motor. O executor dedicado recebe o snapshot fornecido, sem histórico pessoal, integrações, memória, filesystem ou subagentes.

Conceitos e decisões

Idempotência associa uma chave à mesma intenção: um retry não cria nova execução. Compare-and-swap atualiza a linha somente se sua versão ainda é a lida; isso resolve concorrência de workers sem exigir um broker. Um lease delimita a validade do worker: sua expiração marca o resultado como desconhecido e impede uma repetição silenciosa.

Interrupção cooperativa tem uma fronteira concreta. Antes da inferência, o run pode permanecer interrompido. Durante a inferência, pause_requested conserva o resultado ao final e a retomada o publica sem outro LLM. Isso permite testar reinício usando persistência de aplicação; não representa checkpoint arbitrário dentro do grafo. Cancelamento descarta o resultado tardio.

O stream entrega lotes finitos SSE de eventos persistidos, com sequence, timestamp e cursor. O cliente reconecta para obter eventos posteriores. Não há streaming de tokens nesta versão. A origem é plane.session; nenhum evento do navegador vira uma mensagem Telegram fictícia.

Implementação

  1. Contracts fechados definem identidade, contexto, requests, resultados e snapshots.
  2. A migration 0014 cria radar_agent_runs, independente dos ledgers pessoal e de simulação.
  3. AgentRuntimeRepository registra intenção, estado, resultado e eventos. DeepAgentsAdapter reutiliza run_agent e um builder com allowlist vazia.
  4. A API /agent-runtime/v1 exige RADAR_AGENT_RUNTIME_TOKEN; a ausência mantém a superfície desabilitada.
  5. O Plane seleciona um RuntimeCredential de canal plane pertencente ao usuário autenticado, monta um snapshot de até 21 Objects e 40 relações, e revalida o escopo em cada acesso.

Interface

MétodoComportamento
runCria ou recupera a intenção e agenda a execução local.
streamEventos a partir do cursor e snapshot final do lote.
invoke_skillSkill diagnóstica context_summary; desconhecidas são recusadas.
load_contextSnapshot de dados autorizado pelo Plane.
interrupt / resumePausa cooperativa e retomada sem regenerar resultado persistido.
cancelEncerramento lógico e descarte de resultado tardio.

Uma inferência interrompida por queda do processo não é refeita: após 180 segundos, o lease expirado produz unknown. A construção padrão limita o provider a timeout de 120 segundos e zero retries. Unknown precisa de uma nova intenção explícita. Runs queued sobrevivem ao reinício e podem ser retomados por replay/resume.

Configuração e migração

# COS_AGENT_V2: chave exclusiva do host Plane, pelo menos 32 caracteres ASCII
RADAR_AGENT_RUNTIME_TOKEN=<segredo-do-host>
.venv/bin/alembic upgrade head

# Plane, ambiente escolhido explicitamente
RADAR_AGENT_RUNTIME_URL=http://<host-cos>:8000/agent-runtime/v1
RADAR_AGENT_RUNTIME_TOKEN=<mesmo-segredo-do-host>
python manage.py migrate
python manage.py radar_runtime_provision --channel plane \
  --workspace <slug> --admin-id <admin-uuid> --context company:<contexto> \
  --agent-id <agent-uuid> --reviewer-id <user-uuid> --person-id <person-object-uuid>

Os objetos e a Person precisam de vínculos canônicos no contexto. O provisionamento do canal plane retorna o UUID do vínculo para binding_id; não retorna token ao navegador. A chave do host é configuração protegida do servidor. HTTPS é necessário no transporte remoto. As migrations não importam ABox e esta implementação não ativou um ambiente publicado.

Como testar e saber que funcionou

.venv/bin/python -m pytest tests/unit/test_agent_runtime_product.py \
  tests/agent/test_product_runtime_engine.py tests/unit/test_migrations.py

Testes determinísticos comprovam execução única concorrente, escopo, conflito, reinício em pausa, recuperação do resultado sem LLM, cancelamento, lease expirado, auth, cursores e o harness real com modelo scripted. No Plane, test_agent_runtime cobre replay após resposta perdida, falsificação de identidade, contexto obsoleto, revogação e HTTP real entre processos. O contrato do Plane registra os comandos completos e os resultados da validação.

Diagnóstico

503 indica configuração ou transporte indisponível. 404 não confirma existência de um run fora do escopo. 409 exige conferir versão do contexto, grant, intenção e estado terminal. Falhas do provider usam generation_failed, sem expor payload ou segredo. Um stream vazio de eventos pode ser esperado quando o cursor já está atualizado.

Limites e próxima etapa

O contexto usa orçamento de caracteres, não tokens exatos. A execução é somente leitura. Aprovar um comando continua sendo uma operação do Command Layer, não resume deste runtime. A próxima etapa é a configuração estruturada mínima do agente (1.4), seguida de Risk Review e revisão humana na UI. Nenhum segundo runtime de domínio ou catálogo amplo de skills foi criado.

Identidade no produto, execução no adapter e fatos no RADAR.
